# ビジュアライザとデバッグ

スコアの数値は、解がよいか悪いかを教えてくれる。どこが悪いのかは、解を目で見ないとわからない。

## ビジュアライザの使いどころ

- 問題文を読んだ直後。解答例を見て、問題の理解を確かめる
- 最初の解法が動いたとき。予想どおりに動いているかを見る
- スコアが上がらなくなったとき。悪いケースを見て、次の改善を探す
- バグを疑うとき。数値ではわからない誤りが見つかる

## 見るケースの選び方

seed 0だけを見ていると、そのケースに合った改善に偏る。相対スコアが低いケースを選んで見る。入力の条件が極端なケースも見ておく。

## 見るときの問い

- 明らかに無駄な動きや、空いたままの場所はないか
- 人が手で直すなら、どこを直すか
- その直し方は今の近傍や遷移で表せるか

3つ目の問いで「表せない」となったら、それが足すべき近傍だ。

## 自分で出力する情報

公式のビジュアライザが表示しない情報は、標準エラー出力に書く。次の値を出力しておくと役に立つ。

- 反復回数
- 近傍の種類ごとの、試した回数と受理された回数
- 時間ごとのスコアの推移
- 最終スコアと経過時間

反復回数は高速化の成果を測る値だ。近傍ごとの受理の回数は、役に立っていない近傍を見つける手がかりだ。

## デバッグ用の検算

差分計算は、最も誤りが入りやすい部分だ。デバッグ用のビルドでは受理のたびにスコアを最初から計算し、差分で求めた値と比べる。

```cpp
#ifdef LOCAL_DEBUG
assert(std::abs(calc_score(state) - score) < 1e-6);
#endif
```

補助のデータも同じように確かめる。逆引きの配列、グループごとの合計、ハッシュ値などだ。

## 再現できる実行

不具合を調べるには、同じ結果を再現できる必要がある。乱数のシードを固定し、時間の代わりに反復回数で終了するバージョンを用意する。

## よくある誤り

- 最良の解ではなく最後の状態を出力している
- 温度が0に近く、山登り法になっている
- 近傍を選ぶ確率の計算を誤り、一部の近傍しか使われていない
- 整数があふれている
- 配列の範囲の外を読み書きしている

4つ目と5つ目は、コンパイラのオプションで見つけられる。gccなら `-fsanitize=address,undefined` を付けてビルドし、数ケースを実行する。実行は遅くなるので、確認のときだけ使う。

## 多数のケースでの確認

一部のケースでだけ起きる不具合は、少ないケースでは見つからない。提出の前に、数百ケースを実行して、失敗や時間超過がないことを確かめる。
