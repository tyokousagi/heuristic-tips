# ローカルテスト

手元で多数のケースを実行し、スコアを集計する環境を作る。この環境がないと、変更でスコアが上がったのかどうかを判断できない。

## 評価でよくある失敗

- 1つのケースだけで判断する
- 数個のケースを手で実行して判断する
- 提出して暫定スコアで判断する

どれも、ケースの数が足りない。偶然よかっただけの変更を残し、本当によい変更を捨てることになる。提出には回数の間隔の制限もあるので、試せる回数も少なくなる。

## 準備するもの

1. 公式のローカルツールを動かす環境。AHCのツールはRustで書かれているので、Rustを入れておく
2. 入力ファイル。ツールの生成プログラムで、100ケース以上を作る
3. 並列に実行してスコアを集計する仕組み

3つ目には、terry_u16さんの[pahcer](https://github.com/terry-u16/pahcer)が使える。自分で用意する場合は、下のスクリプトから始められる。

これらは、コンテストが始まる前に準備して、過去問で動かしておく。

## 集計スクリプト

[テストの並列実行](/snippets/#run-tests)のスクリプトは、次のように使う。

```bash
python run_tests.py --cmd ./a.out --in-dir tools/in --out-dir out --cases 100 --jobs 8
```

解答プログラムが標準エラー出力に書いた `Score = 数値` の行から、スコアを読む。公式ツールで採点する場合は、採点のコマンドを `--scorer` に渡す。

表示する値は次のとおりだ。

- 正の点数が付いたケースの数
- スコアの平均
- スコアの常用対数の平均
- ケースごとの最高スコアを100としたときの相対スコアの平均
- 最も長かった実行時間
- 失敗したケースの番号と理由

0点以下のケースと、スコアを読めなかったケースは、平均に入れずに失敗として表示する。平均に0点を混ぜると、バグに気づけなくなる。

## ケースの数

ケースの数をx倍にすると、平均のばらつきはおおよそ 1/√x 倍になる。terry_u16さんは次の目安を挙げている。

| 場面 | ケースの数 |
|---|---|
| 短期コンテストで素早く確かめる | 20〜50 |
| 長期コンテストで比べる | 100〜200 |
| 最後の調整とバグの確認 | 500〜3000 |

## 並列実行の注意

物理コアの数より多く並列に実行すると、1ケースあたりの実行が遅くなる。時間いっぱいまで探索する解法では、反復回数が減ってスコアが下がる。比べる2つのバージョンは、同じ並列の数で実行する。

## 実行の記録

実行のたびに、どのコードで実行したかを記録する。予想と違う結果が出たときに、原因を調べられる。gitでコミットしておく方法と、実行のたびにソースをコピーして保存する方法がある。
