# ビームサーチの評価と多様性

ビームサーチの結果は評価関数と、ビームの中にどれだけ違う状態を残せるかで決まる。

## 評価関数の役割

ビームサーチの評価関数は途中の状態から最終的なスコアを予測する関数だ。その時点のスコアだけを使うと、あとで困る状態を見分けられない。

評価関数は次の2種類の項の和として作る。

- ここまでに確定したスコア
- 残りの部分がどれだけうまくいきそうかの見積もり

見積もりの例を挙げる。

- 残っている要素を処理するのに必要な手数の下界
- 目標の位置までの距離の合計
- まだ使える選択肢の数
- あとで困る配置へのペナルティ

eijirouさんはAHC021で、そろえた数に大きな重みを掛けた項と、残りの配置のよさを表す項を足している。

## 評価関数の作り方

1. 確定したスコアだけの評価で動かす。
2. ビジュアライザで結果を見て、どんな状態で困っているかを探す。
3. その状態を悪く評価する項を足す。
4. 多数のケースでスコアを比べ、上がれば残す。

項が増えると重みの調整が必要になる。重みはパラメータにして、あとでまとめて調整する。

## 重複除去

同じ状態がビームに複数あると、その分だけ幅を無駄にする。状態のハッシュ値を計算し、同じ値の候補は評価のよいほうだけを残す。

ハッシュには[Zobrist hash](/techniques/zobrist)を使う。要素が1つ動くたびにXORで更新できるので、候補ごとの計算が軽く済む。

ハッシュに入れる情報は選べる。重要でない要素を外すと、その要素だけが違う状態が重複として除かれ、実質的な多様性が上がる。

## 多様性

評価の上位だけを残すと、ビームが似た状態で埋まる。対策には次の方法がある。

- 同じ親から残す候補の数に上限を設ける
- 位置などの特徴ごとに、残す数の上限を設ける
- 同点の候補は、離れた親の候補が残るように並べる
- 評価値に小さな乱数を足す

chokudaiさんは、ビーム幅が広くても、展開の種類はおおよそ1種類になることがあるとしている。重複除去を工夫するだけでも、多様性は上げられる。

## よくある失敗

評価関数の項を一度に多く足すと、どの項が役に立っているのかがわからなくなる。1つずつ足して比べる。

評価に現れない要素が重要な問題では、評価関数を改善するまでのあいだ、[chokudaiサーチ](/methods/chokudai)のほうがよい結果になることがある。
