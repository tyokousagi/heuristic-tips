# コンテストの進め方

AHCには4時間ほどの短期コンテストと、1週間以上の長期コンテストがあります。どちらも動く解法を早く作り、テストの結果を見て改良を重ねる点は同じです。

## 共通の流れ

1. 問題文を読み、ビジュアライザで解答例を見ます。
2. 形式が正しいだけの自明な解を出力し、提出が通ることを確かめます。
3. すぐ思いつく貪欲法を書き、ビジュアライザで動きを見ます。
4. 手元で多数のケースを実行できる環境を整えます。
5. 貪欲法の問題点から方針を決め、焼きなましやビームサーチに進みます。
6. 変更のたびにテストを実行し、スコアが上がった変更だけを残します。

最初の3つは、問題を理解するための作業です。terry_u16さんは、方針を立てる、実装する、結果を見る、気づきを得るというサイクルを何度も回すことが鍵だと述べています。くわしくは[考察と方針決め](/tips/thinking)にあります。

## 短期コンテスト

短期コンテストでは実装できるかどうかで方針を選びます。4時間で書ききれない方針は、よさそうに見えても選びません。

terry_u16さんがAHC044で記録した時間の使い方は、[時間の使い方と学び方](/tips/time)に載せています。環境の準備に7分、最初の焼きなましが動くまでに23分でした。

テストのケース数は20〜50ほどにして、1回の確認を短くします。ばらつきは大きくなりますが、試せる回数が増えます。

出力の部分は早めに書きます。探索がうまく動いても、正しい形式で出力できなければ0点です。

## 長期コンテスト

長期コンテストでは評価の正確さを上げます。ケース数は100〜200にし、最後の調整では500以上を使います。

序盤は単純な解法で実験して、問題についての理解を深めます。Psyhoさんは、序盤の目的は点数ではなく直感を育てることだと述べています。

近傍が小さすぎるなど、解法の基本の部分に問題があるとわかったら、作り直すことも選択肢です。terry_u16さんはAHC013で、6日目に焼きなましのコードをほぼ捨てて作り直し、そこからスコアを伸ばしています。

後回しにした改善はメモに残します。終盤はパラメータの調整と、多数のケースでの異常終了の確認に使います。

## 提出の判断

暫定テストのケース数は多くありません。手元で多数のケースを比べているなら、手元の結果で提出するバージョンを決めます。確認する項目は[提出前チェックリスト](/workflow/checklist)にまとめています。
